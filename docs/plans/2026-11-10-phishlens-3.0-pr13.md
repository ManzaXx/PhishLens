# PhishLens 3.0 · PR13: reglas propias en JSON y versión 3.0.0. Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** el analista carga un fichero JSON de reglas declarativas (sin regex). Las reglas se validan enteras, se prueban contra el historial y se aplican como un detector más. Con esto se cierra la versión 3.0.0.

**Architecture:**
- `src/rules/validate.js` valida el fichero y devuelve las reglas normalizadas o una lista de errores con regla, ruta y motivo.
- `src/rules/evaluate.js` lee los campos del correo con un mapa explícito de funciones (nunca `obj[campo]`) y aplica operadores de una lista cerrada.
- `src/rules/detector.js` convierte las reglas que se cumplen en hallazgos `custom.<id>`. El motor llama a este detector después de los de PhishLens, pasándole los hallazgos que ya hay.
- La UI añade «Reglas propias» en la portada, junto al interruptor del historial. Las reglas se guardan en un store nuevo `rules` cuando el historial está encendido.

**Tech Stack:** JS del navegador sin dependencias, `node --test`, fuzzing con semilla propio (`tests/fuzz/mutate.js`), Playwright y axe-core.

**Spec:** `proyectoCiber/docs/specs/2026-11-07-phishlens-3.0-design.md`: §5, §6 (fila «Reglas propias»), §7 y §8.

## Global Constraints

- Todo pasa en el navegador. `connect-src 'none'` y la CSP no cambian. Cero dependencias en ejecución.
- **Sin expresiones regulares construidas con texto del usuario.** Ningún `new RegExp(...)` en `src/rules/`. Un test lo vigila sobre el código fuente.
- **Acceso a campos solo con mapas explícitos.** `FIELDS` es un `Map` de nombre a función. Las cabeceras salen de una lista cerrada de 20 nombres. Nunca se usa `obj[texto del usuario]`.
- **Topes:**
  - 200 KB por fichero y 100 reglas;
  - 4 niveles de `all`/`any`/`not` y 20 condiciones por regla;
  - 200 valores en `in` y `not-in`;
  - `id` de 3 a 64 caracteres de `[a-z0-9.-]`, único;
  - `title` de hasta 120 caracteres y `detail` de hasta 300.
- **Comparación:** sin distinguir mayúsculas, con `String.prototype.normalize('NFKC')` y `toLowerCase()` en los dos lados.
- `severity` puede ser `low`, `medium` o `high`. `category` sale de `CATEGORIES`. `technique` tiene que existir en `TECHNIQUES` de `data/mitre.js`.
- Una regla propia **nunca baja la puntuación**: sus hallazgos tienen polaridad `risk` y gravedad `low` o más.
- Todo lo que viene del fichero de reglas se pinta con `textContent`. Nunca se usa `innerHTML`.
- Textos en español, sin jerga innecesaria. Tokens de `tokens.css`.
- `VERSION` y `package.json` pasan a `3.0.0` en la Tarea 4, no antes.

## Decisiones (Rulings) que este plan toma

1. **Los hallazgos llevan el id `custom.<id>`.** Así nunca chocan con un id de PhishLens. `finding.id` solo mira los hallazgos de PhishLens, no los de otras reglas propias: no hay cadenas entre reglas propias.
2. **Dónde está «Ajustes».** La app no tiene página de ajustes. «Reglas propias» va como un `<details>` en la portada, debajo del interruptor del historial, con:
   - el botón «Cargar reglas (.json)»;
   - la lista de errores;
   - la vista previa;
   - «Activar reglas» y «Quitar reglas».
3. **Vista previa.** Para cada regla dice cuántos análisis guardados la cumplirían.
   - Solo se puede calcular si la regla usa únicamente `finding.id`. Con cualquier otro campo dice «No se puede probar con el historial: necesita el correo, y el correo no se guarda».
   - Con el historial apagado o vacío dice «Sin análisis guardados para probarla».
4. **Al activar las reglas**, el análisis abierto se vuelve a analizar si su texto sigue en memoria. Un análisis abierto desde el historial no se vuelve a analizar, porque no tiene el correo. Los lotes aplican las reglas activas a cada correo.
5. **Dónde se guardan las reglas.** Van en el store `rules` (`DB_VERSION` 2, con una sola entrada `{ id: 'active', source, rules, savedAt }`) solo si el historial está encendido. Si no, duran lo que dure la pestaña.
   - «Borrar todo» las borra con la base. La UI lo dice: «Reglas propias quitadas».
   - Encender el historial con reglas activas las guarda.
6. **Rendimiento.** Cada campo se normaliza una sola vez por análisis, en una caché `Map` local a `evaluate`. `body.text` se recorta a los mismos `LIMITS` que ya usa el parser.
7. **Marca «Regla propia».** Va en `findingCard`, en la tabla de hallazgos del informe forense y en el texto llano (`plain` = el `title` de la regla). Los hallazgos llevan `detector: 'custom'`, `provenance: 'declared'`, `reliability: 'medium'` y `custom: true`.
8. **El JSON Schema** (`docs/rules.schema.json`, 2020-12) es solo documentación. La validación la hace `validate.js`. Un test comprueba que el ejemplo de `docs/rules.md` pasa `validate.js`.

## Review Focus

1. **Ficheros hostiles.** Un fichero con `__proto__`, `constructor` o `prototype` como clave, o con `"field": "__proto__"` o `"header:__proto__"`, se rechaza con su error. `Object.prototype` sigue intacto. Test en la Tarea 1.
2. **Unicode.** `ＦＡＣＴＵＲＡ` (ancho completo) y `Factura` cumplen `contains "factura"`. Un nombre de adjunto con RLO se compara con el RLO, y en pantalla sale revelado. Test en la Tarea 2.
3. **Correos sin datos.** Con una URL suelta, texto pegado sin cabeceras, sin adjuntos o sin `Reply-To`, cada campo ausente hace que la condición no se cumpla (`exists` da falso, `not-in` sobre un campo ausente también da falso) y nada lanza. Test en la Tarea 2.
4. **Una regla nunca baja la nota.** Prueba de propiedad: para las 13 muestras y 200 reglas aleatorias válidas, la puntuación con reglas es mayor o igual que sin ellas. Test en la Tarea 2.
5. **Historial apagado y «Borrar todo».** Con el historial apagado, cargar reglas no crea la base. Con el historial encendido, las reglas siguen tras recargar y desaparecen con «Borrar todo». e2e en la Tarea 3.

### Task 1: Validador de reglas

**Files:**
- Create: `src/rules/validate.js`, `tests/unit/rules-validate.test.js`, `tests/fuzz/rules.test.js`

**Interfaces:**
- Produces:
  - `RULES_LIMITS = { fileBytes: 200 * 1024, rules: 100, depth: 4, conditions: 20, values: 200 }`.
  - `HEADER_FIELDS`: lista congelada de 20 cabeceras: `from`, `to`, `cc`, `reply-to`, `return-path`, `sender`, `subject`, `date`, `message-id`, `x-mailer`, `user-agent`, `x-originating-ip`, `x-priority`, `importance`, `list-unsubscribe`, `authentication-results`, `received-spf`, `x-spam-status`, `x-ms-exchange-organization-scl` y `content-type`.
  - `FIELD_NAMES`: los campos de §5.1, más `header:<nombre>` para los de `HEADER_FIELDS`.
  - `OPERATORS`: `equals`, `contains`, `starts-with`, `ends-with`, `in`, `not-in`, `exists` y `count-gte`.
  - `LIST_FIELDS`: `link.domain`, `link.url`, `attachment.name`, `attachment.extension`, `attachment.type`, `attachment.sha256` y `finding.id`.
  - `validateRules(text: string) → { ok: true, rules: Rule[] } | { ok: false, errors: { rule: number|null, path: string, reason: string }[] }`.
  - `Rule = { id, title, detail, severity, category, technique|null, when }`, con los valores ya pasados por NFKC y minúsculas, y `when` como un árbol de objetos planos nuevos.
  - `formatRuleError(e) → string`, con el formato exacto «Regla 3, `when.all[1].op`: «matches» no es un operador admitido». Si `rule` es `null`, empieza por «Fichero: ».
