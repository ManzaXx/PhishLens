# PhishLens 2.2 · PR 1 — Reestructura y nuevo modelo de hallazgo · Plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Reorganizar `proyectoCiber/src` y `tests` según la arquitectura de la 2.2 y ampliar el email parseado y el hallazgo, sin cambiar ningún veredicto.

**Architecture:** Se fija primero una «foto» (golden) de los informes de las 7 muestras con el código actual; después se mueven ficheros y se amplían modelos, y la foto debe seguir siendo idéntica en los campos que ya existían. Todo lo nuevo es aditivo: `headerList`, `rawBody`, `parseNotes`, bytes y SHA-256 de adjuntos, y los campos `category`, `reliability`, `provenance`, `polarity` y `techniques` del hallazgo.

**Tech Stack:** JavaScript con módulos ES, `node --test` (Node 22), sin dependencias.

**Spec:** `proyectoCiber/docs/specs/2026-11-05-phishlens-2.2-design.md` (§2, §3, fila «PR 1» de §10).

## Global Constraints

- Cero dependencias en tiempo de ejecución; ninguna petición de red.
- No tocar `WebDeBicis/` ni `ManzaXx/WEB1`.
- Regla de dependencias: `ui → core → (detectors, auth, intel) → parser → (data, lib)`. `lib/` no importa nada interno.
- `proyectoCiber/` debe funcionar como raíz de un repo independiente (sin rutas a `../`).
- Ningún test existente cambia sus aserciones; solo sus rutas de import.
- Commits con el pie de atribución de la sesión.

**Desviación de la spec:** `limits.js` va en `lib/` y no en `core/`, porque lo usa el parser y la regla de dependencias no deja que `parser` importe `core`.

## Review Focus

1. **Adjunto base64 corrupto o truncado:** `bytes` vacío o parcial, `sha256` del contenido decodificado, sin excepción. Test en la Task 4.
2. **Adjunto mayor que `LIMITS.attachmentBytes`:** se guardan los bytes hasta el límite, `truncated: true`, el hash es `null` (un hash parcial engañaría como IOC) y se anota `limit.attachment-bytes` en `parseNotes`. Test en la Task 4.
3. **Cabeceras con plegado (líneas que empiezan por espacio o tabulador) y CRLF:** `headerList[].raw` conserva el texto exacto, incluidos los saltos, porque DKIM lo necesitará. Test en la Task 4.
4. **Multipart sin delimitador de cierre:** se procesa lo que haya y se anota `mime.unterminated-multipart`. Test en la Task 4.
5. **Detector externo que crea hallazgos con `finding()` sin pasar los campos nuevos:** recibe los valores por defecto de su detector; un detector desconocido usa `category: 'infrastructure'`, `reliability: 'low'`. Test en la Task 5.

### Task 4: Email parseado ampliado

**Files:**
- Modify: `src/parser/eml.js`
- Test: `tests/unit/eml-raw.test.js`

**Interfaces:**
- Consumes: `sha256`, `LIMITS` (Task 3).
- Produces, en el objeto que devuelve `parseEml(raw)`:
  - `headerList: [{ name: string (minúsculas), value: string (decodificado, igual que en headers), raw: string (líneas originales con plegado y saltos, sin el salto final), index: number }]`
  - `rawBody: string` (cuerpo tras la línea en blanco, recortado a `LIMITS.rawBytes`)
  - `parseNotes: [{ code: string, detail: string }]`; códigos: `limit.depth`, `limit.parts`, `limit.attachments`, `limit.links`, `limit.attachment-bytes`, `limit.raw-bytes`, `mime.unterminated-multipart`
  - `attachments[]: { filename, contentType, size: number, bytes: Uint8Array, sha256: string | null, truncated: boolean }`
  - `emptyEmail()` y `emailFromUrl()` incluyen `headerList: []`, `rawBody: ''`, `parseNotes: []`.

- [ ] **Step 1:** Escribir los tests:
  - `headerList conserva orden y crudo`: con `'Received: a\r\n\tb\r\nFrom: x@y.test\r\nReceived: c\r\n\r\nhola'`, `headerList.map(h => h.name)` → `['received','from','received']`, `headerList[0].raw` → `'Received: a\r\n\tb'`, `headerList[0].value` → `'a b'`.
  - `rawBody es el cuerpo exacto`: `rawBody` → `'hola'`.
  - `adjunto base64 → bytes y sha256`: parte `Content-Disposition: attachment; filename="a.txt"` con base64 de `'abc'` → `bytes` igual a `[97,98,99]`, `size` 3, `sha256` = vector de `'abc'`, `truncated` false.
  - `adjunto quoted-printable y 7bit`: los bytes coinciden con el contenido decodificado.
  - `base64 corrupto no lanza`: `'@@@'` → `bytes.length === 0`, `sha256` = hash vacío.
  - `adjunto mayor que el límite`: con `LIMITS.attachmentBytes` bajado a 4 temporalmente (restaurar en `finally`) y contenido de 10 bytes → `bytes.length === 4`, `truncated === true`, `sha256 === null`, `parseNotes` contiene `limit.attachment-bytes`.
  - `multipart sin cierre anota`: boundary sin `--b--` → `parseNotes` contiene `mime.unterminated-multipart`, y el texto de la parte se lee igual.
  - `límite de partes anota`: 600 partes → `parseNotes` contiene `limit.parts` (una sola vez).
  - `entrada sin cabeceras`: `headerList` `[]`, `parseNotes` `[]`.
- [ ] **Step 2:** Ejecutar `node --test tests/unit/eml-raw.test.js`. Esperado: FAIL.
- [ ] **Step 3:** Implementar. `parseHeaders` pasa a construir también `headerList`, acumulando las líneas crudas de cada cabecera. `walkPart` recibe `acc.notes` y anota cada límite una sola vez (un `Set` de códigos). Para adjuntos, decodificar con `base64ToBytes` / `qpToBytes`, o para 7bit/8bit/binary con `Uint8Array.from(body, c => c.charCodeAt(0) & 0xff)`. El cierre del multipart se detecta si ningún trozo empieza por `--`.
- [ ] **Step 4:** Ejecutar `node --test`. Esperado: todo en verde, golden incluido (`legacyView` ignora los campos nuevos de los adjuntos porque solo copia `filename` y `contentType`).
- [ ] **Step 5:** Commit: `feat(proyectoCiber): headerList, rawBody, parseNotes y bytes de adjuntos`.
